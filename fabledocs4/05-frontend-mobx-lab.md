# 05 — Frontend Lab: Stores, Models, Shipped Policies, and One Real Feature

fabledocs2/3 are server-heavy on purpose — that's where this codebase's
hardest decisions live. But you will ship frontend work here, and the `app/`
tree has its own architecture worth a deliberate half-day. This lab is
hands-on: run `yarn dev:watch`, open the React devtools, and keep
`app/stores/base/Store.ts` open in a split the whole time.

## Part 1 — The shape of the frontend (45 min, read + poke)

The SPA is React + **MobX class stores**, not Redux/hooks-state/React Query.
The pattern, one sentence: observable **model** instances
(`app/models/Document.ts`) live in typed **stores**
(`app/stores/DocumentsStore.ts`) that all hang off one `RootStore`
(`app/stores/RootStore.ts`), and components observe them.

Read in this order:

1. `app/stores/base/Store.ts` — the generic base. Find:
   - the `RPCAction` enum (`Info`, `List`, `Create`, `Update`, `Delete`,
     `Count`) and how `fetch`/`save`/`delete` derive endpoint names from the
     model name. This is ADR-003's client half: the API is so regular the
     client is *generated by convention*.
   - the observable `data` map and how `add` upserts model instances so
     every part of the UI sees one shared instance per id (identity map —
     the pattern's whole point).
2. `app/models/base/Model.ts` + `app/models/decorators/` — `@Relation` and
   the `LifecycleManager`: relations between models are declared, and
   deletes cascade client-side via `getInverseRelationsForModelClass`.
   Compare with the server's Sequelize associations — same graph, two
   runtimes (ADR-002 again).
3. `app/models/Policy.ts` and one consumer — grep `usePolicy` or `can(` in
   `app/` (menus are the richest: `app/menus/`). This is ADR-004's payoff:
   the Delete menu item renders from the *server's* ability serialization,
   not from a client-side role check.
4. `app/stores/AuthStore.ts` + `app/stores/index.ts` — how stores
   instantiate and how components reach them (`useStores` hook in
   `app/hooks/`).

**Checkpoint questions** (answer from code, not vibes):
- When a websocket event says a document changed, which code path updates
  the sidebar? (Find the socket message handling in `app/` — trace from
  where socket.io client connects — and watch it call into stores. The
  server half is `WebsocketsProcessor`; find the client half.)
- Why does `Store.add` upserting into one map matter for a document that's
  open in the editor *and* visible in the sidebar?

## Part 2 — Break it on purpose (30 min)

Two five-minute sabotages, done locally, reverted after. Predict before each:

1. In a menu component that checks a policy ability, invert the check
   (render the action when `can.update` is false). Click it. **The point:**
   the server still 403s — the button was UI *affordance*, authorization
   never left the server. Now you've *seen* defense-in-depth rather than
   read about it.
2. In `Store.ts`, find where a model is added after `fetch`, and make it
   create a fresh instance instead of upserting. Open the same document in
   sidebar + editor and edit the title. Watch them disagree. That's life
   without the identity map — and why "just use plain objects" loses to
   this architecture for an app where one entity appears in six places.

## Part 3 — Ship a feature end-to-end (2–3 hrs)

Build **"word count in the document info dialog"** — deliberately small, so
the learning is the *route through the layers*, not the feature. It answers
fabledocs2 doc 02's exit question 3 for real.

Server (you know this drill from fabledocs2/3):

1. `server/routes/api/documents/schema.ts`: add `DocumentsWordcountSchema`
   (just `id`, reuse the id type helpers already imported there).
2. `server/routes/api/documents/documents.ts`: add `documents.wordcount` —
   pipeline order matters: rate limit is inherited, add `auth()`,
   `validate(schema)`; **no** `transaction()` (read-only — know why you're
   omitting it, that's the lesson). Load via `documentLoader` (see how
   `documents.info` does it), `authorize(user, "read", document)`, compute
   from the text helper (`DocumentHelper` in `server/models/helpers/` — find
   the text/plain serialization used elsewhere rather than writing your own),
   return `{ data: { total } }`.
3. Which representation did you just count — `text`, `content`, or `state` —
   and how stale can it be (ADR-007)? Write the one-line comment in the
   handler stating the staleness contract. Reviewers of real PRs here should
   demand that comment.
4. Route test per ADR-010: happy path, 403 for a cross-team factory user,
   404-shaped behavior for a deleted doc. Look at a neighbor test in
   `server/routes/api/documents/documents.test.ts` and match its style.

Client:

5. `app/models/Document.ts`: no new store needed — add a method or use the
   API client directly from the dialog. Decide: does word count belong in
   the model (cached, observable) or as a fetch-on-open in the component?
   Defend your choice in one sentence (hint: how stale is acceptable, and
   does any other component need it?).
6. Find the document info/details UI (grep `Info` in `app/scenes/Document/`
   or the document menu) and render the count with a loading state.
7. i18n: wrap the label with the translation function like every neighboring
   string (`t("Words")`) — `yarn build:i18n` exists for a reason and review
   will catch a hardcoded string.

**Definition of done:** feature works in the browser; server test green
(`yarn test:server`); `yarn lint` clean; and you can narrate the request's
full path — middleware pipeline, policy check, representation read, presenter
— without notes. That narration *is* the deliverable; the feature is scaffolding.

## Exit questions

1. What does the frontend `RPCAction` convention buy, and what does a
   deviation from the naming convention cost the client?
2. Why must authorization UI checks (`Policy`) and server `authorize()` agree
   automatically in this architecture — which ADR makes that structural?
3. Your word count read `text`. A user typing right now sees a stale count.
   Explain to a PM, in two sentences, why that's correct behavior and what
   it would cost to make it live.
